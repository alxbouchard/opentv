# Plan — Prototype OpenTV Raspberry Pi 4 (« Pi neuf → HDMI → QR → config → OpenTV → agent »)

Statut : MVP implémenté et vérifié **hors matériel** (macOS/Linux, rootfs temporaire). Aucune Pi n'a été
utilisée : rien n'est déclaré plug-and-play tant que la checklist terrain de `scripts/pi4/README.md` n'est pas
passée sur une vraie Raspberry Pi 4. Ce plan fixe les choix avant le code.

## Objectif

Une Raspberry Pi 4 neuve (Raspberry Pi OS Lite Bookworm 64-bit — dans Raspberry Pi Imager : « Raspberry Pi OS
(Legacy, 64-bit) Lite », l'entrée par défaut étant désormais Trixie — préparée par Raspberry Pi Imager) branchée en
HDMI sur une TV affiche OpenTV en plein écran. Au premier démarrage, la TV montre un QR ; le téléphone ouvre un
formulaire local (Wi-Fi, nom de l'appareil, agents autorisés). Ensuite la TV affiche un tableau de bord français
« Pour toi » (moteur existant réutilisé) et un agent local (Muse, Hermit, Hermes) peut se brancher par MCP stdio
avec des outils bornés.

## Séparation avec la production (non négociable)

- `native/` (Tizen v23) et `scripts/nanopi/` (NanoPi M4B, pont Films/« Pour toi », autostart) **ne sont pas
  modifiés**. Les fichiers racine TizenBrew non plus.
- La Pi 4 n'est **pas** une copie du NanoPi : aucun flag ni périphérique Rockchip (`/dev/mpp_service`,
  `/dev/video-dec0`, Mali, `--disable-gpu`, weston pixman). Pile officielle Raspberry Pi : KMS `vc4-kms-v3d`,
  Cage (Wayland), Chromium de Raspberry Pi OS, NetworkManager, systemd.
- La Pi ne remplace pas les applis Samsung (YouTube, Netflix…) : elle est une source HDMI qui affiche le
  tableau de bord OpenTV, « Pour toi » et les messages d'agents. Le lanceur d'applis natives reste la TV ; l'écran
  « Pour toi » le rappelle par une ligne discrète.
- Aucun flux média extrait/proxy/reconstruit. MVP : métadonnées du catalogue accepté uniquement (fichier
  `catalogue.json` produit ailleurs et importé), pas de lecture.

## Réutilisation du moteur « Pour toi »

`scripts/nanopi/opentv_foryou.py` (et sa dépendance `opentv_bridge.py`, utilisée seulement pour
`load_catalogue_meta`) est installé **tel quel** sous `/opt/opentv/lib/foryou/` avec son hash au manifeste.
L'adaptateur `opentv_pi/foryou.py` le charge par chemin explicite et appelle :
- la **CLI** `opentv_foryou.main([...])` en mémoire pour les outils agents (validation, bornes, `scrub`) ;
- l'objet `Bridge` du moteur pour la vue TV : `Bridge.session(items)` (sélection figée, rechargée au plus toutes
  les 120 s ; coût sur Pi 4 à mesurer sur le terrain) et `Bridge.act(session, uid, action)` pour les avis
  (affiches https uniquement en loopback).
Aucune logique de recommandation n'est copiée. Aucun refactor du moteur.

## Architecture (`scripts/pi4/`)

  nmkeyfile.py           profils NetworkManager (keyfile) échappés, jamais en argv

  nethelper.py           côté root : consommation unique d'un job validé, nmcli argv sans shell, budget 120 s

  foryou.py              adaptateur du moteur « Pour toi » (CLI + vue TV)

## Décisions

1. **Premier démarrage** : non configuré ⇒ mode configuration. Ethernet (ou Wi-Fi Imager) avec IPv4 ⇒ QR vers
   `http://<ip-lan>:8081/setup?t=<jeton>`. Sans IP après `HOTSPOT_GRACE_S` ⇒ point d'accès NetworkManager
   `OpenTV-XXXX` (WPA2, mot de passe éphémère affiché seulement sur la TV) puis QR `http://10.42.0.1:8081/…`.
   Le hotspot est **borné et fail-closed** : désactivable (`HOTSPOT_ENABLED=0`) ; durée maximale
   `HOTSPOT_MAX_S` (20 min par défaut) depuis son premier démarrage, persistée par `boot_id` (un redémarrage du
   service ne la remet pas à zéro) ; à l'échéance `ap-stop` (profil supprimé), aucune rediffusion, message TV
   « Ethernet ou redémarrer la boîte » ; réarmement par redémarrage, `setup reset` ou « Reconfigurer ». L'AP est
   détecté même derrière Ethernet (`ap_active`) : toute configuration réussie l'arrête, AP orphelin arrêté.
   **Garde root indépendante** `opentv-ap-guard.timer` (30 s) → `opentv-pi ap-guard` (oneshot, argv fixes) : arrêt +
   suppression de `opentv-setup-ap` si `opentv.service` n'est pas `active`, configuration invalide, `boot_id` inconnu,
   budget absent/autre démarrage/expiré/négatif/dépassé (+30 s). `boot_id` illisible ⇒ aucun hotspot automatique ni
   réarmement, message TV honnête. `uninstall.sh` (normal et `--purge`) arrête la garde puis l'AP avant tout retrait.
   Jamais vérifié sur Pi dans ce lot.
2. **Jeton** : `secrets.token_urlsafe`, TTL 10 min, usage unique (consommé par la soumission valide), 5 essais
   de formulaire, hash seul pour la comparaison, rotation affichée par la TV, jamais sur disque ni dans un
   journal. Seules les **soumissions** (POST) **avec le bon jeton et un formulaire invalide** usent les essais : un
   GET ou un POST avec un jeton faux est refusé sans brûler le QR (jetons faux limités à 30/min par IP, table bornée).
   Le serveur LAN (8081) n'existe que pendant la configuration et ne sert que `/setup`. **Limite assumée** : HTTP non
   chiffré ; par Ethernet le mot de passe Wi-Fi traverse le LAN en clair ⇒ configuration réservée à un LAN de
   confiance (ou au hotspot WPA2 local à clé affichée sur la TV).
3. **Wi-Fi** : le service (utilisateur `opentv`, sans privilège) écrit un job JSON 0600 (O_EXCL) dans
   `/var/lib/opentv/netjobs/`. `opentv-net-helper.path` déclenche le helper root qui vérifie propriétaire, mode,
   type, taille, âge, **supprime le job avant d'agir**, revalide, écrit un profil NetworkManager **candidat**
   (`opentv-wifi-candidate`, keyfile 0600, UUID neuf, autoconnect=false, dans `/etc/NetworkManager/system-connections/`)
   puis `nmcli connection load` + `up uuid` en argv fixe (`shell=False`). L'ancien `opentv-wifi` n'est touché qu'après
   succès (keyfile final au même UUID que le candidat, rename atomique, `load`) ; échec/délai ⇒ candidat supprimé et
   ancien remonté (`up uuid`, ou hotspot si configuration hors ligne) dans une réserve de 51 s fixée avant l'essai. Le mot de passe n'apparaît jamais en argv, en journal ni dans le résultat.
   Budget réel d'une activation du helper : 120 s (≪ `TimeoutStartSec=180`), `nmcli --wait` courts, délais tronqués au
   budget restant, groupe de processus tué ; `wifi-apply` refusé s'il est pris > 60 s après dépôt. Côté service,
   échéance persistée de 210 s (`wifi-apply.json`, même `boot_id`) : au-delà échec honnête, job retiré, nouveau QR,
   résultat tardif ignoré ; le hotspot ne repart que dans son budget. Le drapeau de configuration reste posé tant que le
   Wi-Fi n'est pas confirmé (un redémarrage du service ne « termine » pas la configuration).
4. **Kiosque** : Cage sur tty1 (PAM dédié, utilisateur `opentv-kiosk` groupes video/render/input), Chromium
   Raspberry Pi OS en Wayland, profil **persistant** dédié `/var/lib/opentv-kiosk/chromium` (verrous effacés au
   lancement, aucun secret durable), `Restart=always`. Le lanceur teste seulement l'ouverture du **port TCP**
   loopback (20 s, pas `/healthz`) et sinon ouvre la page de secours locale, qui interroge `/healthz` et revient au
   tableau de bord dès que le service répond. Clé de page renouvelée à chaque démarrage du service : un 403
   explicite `tv_key` déclenche un rechargement de `/tv` sondé et borné (2/4/8 s, 3 par 10 min, `sessionStorage`) ;
   sonde en échec ⇒ attente doublée jusqu'à 60 s. Page de secours `file://` + `fetch` loopback : compatibilité Local
   Network Access **non vérifiée** sur le Chromium de Raspberry Pi OS (gate terrain, README §8).
   1080p : `install.sh` ajoute toujours `video=HDMI-A-1:1920x1080@60` à `cmdline.txt` (sauvegardé, retiré par
   `uninstall.sh`, rollback en cas d'échec) + `wlr-randr` dans Cage.
5. **CEC** : découverte seulement (`/dev/cec*`, `cec-ctl -d <dev>` sans émission). Aucune commande d'alimentation.
6. **Agent Port** : socket Unix 0660 groupe `opentv-agent`, jeton par agent (sha256 au registre 0600), scopes
   `read`, `feedback`, `display`, débit et verrouillage **par UID** (`SO_PEERCRED`). Le QR enregistre explicitement
   la politique des trois agents connus, « aucun accès » compris (scopes vides) ; une fois définie, elle plafonne
   `opentv-pi agent issue` (agent inconnu ou scope en trop refusé sauf `--force` sur la boîte) ; sans politique
   (avant configuration), l'administrateur local émet librement. L'émission du fichier client 0600 se fait sur la
   boîte, jamais par le réseau : sous root, dans `/etc/opentv/agents/agent-<id>-<uid>.json` (dossier root:root 0755
   vérifié composant par composant, fichier root:<groupe privé> 0640 écrit par descripteur, `--out` refusé, aucun
   accès au home du compte) ; échec d'écriture ⇒ jeton annulé (entrée précédente restaurée). Aucune URL ni secret en sortie,
   audit JSONL expurgé (outil, statut, durée, tailles). Relais sortant futur : documenté, `status` répond
   `not_implemented`.
7. **Installation** : `prepare-pi.sh` exécute un préflight **matériel** strict (Pi 4, rpi-issue, Bookworm,
   arm64, KMS, DRM, cmdline) **avant tout apt** et liste à part les dépendances absentes qu'il installe.
   `install.sh [--dry-run] [--root DIR]` (rootfs de test sans root) : préflight complet, sauvegardes, manifeste
   SHA-256, retrait (sauvegardé) des fichiers de l'ancien manifeste absents du nouveau, 1080p noyau, `restart` des
   services (mise à jour), retour arrière automatique sur tout échec avant le manifeste ; après ce point de
   non-retour (sysusers, tmpfiles, systemctl), arrêt explicite avec la commande `uninstall.sh` (pas de faux rollback) ; `uninstall.sh` (restaure les sauvegardes et
   `cmdline.txt`, `--purge` optionnel), `opentv-pi health`. Pi 5 : refusé (futur).
8. **Watchdog** : tick borné (`nmcli` 3 s + `ip` 2 s, groupe de processus tué à l'échéance, CEC en thread) +
   attente 2 s, très en dessous de `WatchdogSec=30` (vérifié par test). Résidus du dossier des jobs réseau
   supprimés sans action : `opentv-net-helper.path` ne boucle jamais.

## Revue qualité n°2 (REQUEST_CHANGES → corrigé, `test_review2.py`)

- **Critique** : root n'écrit plus jamais dans le home d'un agent (`agent issue --owner`) ; fichier client root-owned
  dans `/etc/opentv/agents/`, `dir_fd`/`O_EXCL`/`O_NOFOLLOW`/rename, `fchown`/`fchmod` sur le descripteur, rollback
  du jeton si l'écriture échoue. Tests : `~/.config`, `~/.config/opentv`, destination en liens, home absent.
- **Toutes les opérations root par chemin** remplacées (`fsutil.py`) : `setup reset` (O_NOFOLLOW|O_NONBLOCK, fichier
  régulier à lien unique, propriétaire attendu), registre/politique, résultats et dossier des jobs du helper,
  keyfiles. Tests avec `os.chown`/`os.chmod` piégés, liens, FIFO, lien dur, dossier remplacé par un lien.
- **Wi-Fi transactionnel** : candidat `opentv-wifi-candidate` (UUID neuf, autoconnect=false), promotion par rename
  atomique du keyfile après succès seulement, retour arrière (candidat supprimé, ancien remonté ou hotspot) dans une
  réserve de budget fixée avant l'essai.
- **Mineurs** : jetons faux sans effet sur le QR (+ 30/min/IP, table bornée) ; serveurs HTTP/Agent Port à 16
  connexions (503/`busy`), échéance globale anti-slowloris ; kiosque `StartLimitIntervalSec=0` ; journal HTTP sans
  polls 200 (échantillon) ; `install.sh` explicite après le point de non-retour ; HTTP LAN non chiffré documenté.
